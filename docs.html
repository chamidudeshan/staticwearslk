Project Documentation

Static Wears

A full-stack e-commerce platform built as a microservices monorepo. This doc covers every part of the project - how it's structured, how the pieces talk to each other, and what actually happens when someone buys a t-shirt.

Monorepo

Project structure

The whole thing lives in one Git repository managed by pnpm and Turborepo. pnpm handles dependencies with a shared cache so packages don't get duplicated, and Turbo handles the build order so everything compiles in the right sequence.

There are two kinds of things in the repo - apps (things that actually run) and packages (shared code that the apps import).

folder tree 
staticwears/
├── apps/
│   ├── storefront/          - the customer-facing shop (port 3000)
│   └── admin/               - the admin panel (port 3001)
│
├── packages/
│   ├── shared/              - types + supabase clients used everywhere
│   ├── kafka/               - event bus (publish/consume messages)
│   ├── product-service/     - all product/category/brand DB queries
│   ├── order-service/       - order creation and lookups
│   ├── user-service/        - user profile queries
│   ├── payment-service/     - stripe, paypal, payhere logic
│   └── email-service/       - sends emails via Resend
│
├── docker-compose.yml       - runs everything in production
├── .gitlab-ci.yml           - auto-deploys on every push to main
└── turbo.json               - tells turbo how to build in order

The apps import from packages using workspace aliases like @static-wears/shared or @static-wears/order-service. This means the business logic lives in one place - not duplicated between storefront and admin.

How Turborepo fits in

When you run pnpm run build from the root, Turbo looks at which packages depend on which others and builds them in the right order. So shared always builds before product-service, and product-service before the apps. Without Turbo you'd have to do this manually.

Architecture

Microservices architecture

Static Wears is built as a microservices monorepo. Each service owns a specific domain - products, orders, payments, emails - and nothing crosses those boundaries without going through the defined interface. They all live in one repo for convenience, but they're completely independent of each other at runtime.

In a traditional monolith, the checkout page might directly query the database, send the email, and update the stock in one big function. Here, each of those things is a separate service with one job. The storefront orchestrates them but doesn't own their logic.

Communication patterns

Services talk to each other in two ways depending on whether the caller needs to wait for the result.

Synchronous - direct import

When the storefront needs a product list to render a page, it imports getProducts() from product-service and calls it directly. This is a regular TypeScript function call - fast, synchronous, and the response goes straight into the page render.

example - storefront fetching products synchronously 
import { getProducts } from '@static-wears/product-service';

// called in a server component - blocks until data is ready
const products = await getProducts({ category: 'hoodies', limit: 12 });

Asynchronous - Kafka events

When an order is placed, the storefront doesn't need to wait for the confirmation email to be sent before telling the user their order went through. So instead of calling the email service directly, it publishes an event to Kafka and moves on. The email-worker picks it up whenever it gets to it.

example - storefront publishing an event and not waiting 
import { publishEvent, TOPICS } from '@static-wears/kafka';

// don't await - fire and move on
publishEvent(TOPICS.ORDER_PLACED, { orderId, to, items, total })
  .catch(console.error);

The rule is simple: if you need the result to continue, use a direct import. If the caller doesn't care about the outcome (emails, alerts, notifications), use Kafka.

Why monorepo and not separate repos?

The services are logically separate but share TypeScript types from the shared package. If products, orders, and the storefront each lived in their own repo, keeping the types in sync would mean publishing npm packages and versioning them. In a monorepo, a change to a type in shared is immediately visible to everything else - and TypeScript will break the build if something doesn't match, before anything gets deployed.

Turborepo handles the build order so each package only builds after its dependencies are ready. pnpm's workspace protocol (workspace:*) links local packages together instead of pulling from npm.

package.json in storefront - how it references local packages 
{
  "dependencies": {
    "@static-wears/shared":          "workspace:*",
    "@static-wears/product-service": "workspace:*",
    "@static-wears/order-service":   "workspace:*",
    "@static-wears/kafka":           "workspace:*"
  }
}

How data flows across services (full example)

Here's the complete path when an admin changes an order status to "Shipped":

  1. Admin clicks "Mark as Shipped" in the admin panel
  2. Admin panel calls PATCH /api/admin/orders/[id] with { status: 'shipped' }
  3. API route calls updateOrderStatus(id, 'shipped') from order-service
  4. order-service updates the row in Supabase
  5. order-service publishes an ORDER_STATUS_CHANGED event to Kafka with the order details
  6. email-worker picks up the event from Kafka
  7. email-worker calls sendShippingUpdate() from email-service
  8. email-service calls the Resend API
  9. Customer gets an email saying their order shipped

Steps 5-9 all happen asynchronously after the API route already returned a 200 to the admin. The admin sees "Status updated" instantly - the email goes out a few seconds later.

Component library

The admin uses shadcn/ui components (Button, Input, Table, Badge, Dialog, Select, etc.) installed individually into src/components/ui/. These are copy-pasted, not a dependency - so they can be customised freely. The storefront uses handwritten components since the design is more bespoke.

Storefront design decisions

  • Font: Geist Sans + Geist Mono loaded via next/font/google - zero layout shift, auto-optimised
  • Dark-only: The storefront doesn't have a light mode - the brand aesthetic is dark. bg-brand-dark is the base of every page.
  • Product gallery: Color-tab based - clicking a colour swatch swaps the image set, not just one image. Each colour has its own image array from the DB.
  • Cart drawer: Opens as a right-side slide-over on add-to-cart, not a page navigation. Uses a React Context to control visibility.
  • Marquee strip: CSS animation (@keyframes marquee) on a duplicated text node. Content comes from site_settings.marquee_text in Supabase.
  • Banner slider: Auto-advances every 5 seconds, pauses on hover, respects prefers-reduced-motion. Images and text from the banners table.

Admin design decisions

  • Sidebar layout: Fixed left sidebar with nav links, main content area scrolls independently.
  • Mobile nav: Sidebar collapses to a hamburger menu on small screens. Full-screen overlay nav on mobile.
  • Status badges: Each order status (pending, confirmed, shipped, etc.) has a specific colour badge. Defined in a STATUS_COLORS map.
  • Drag to reorder: Banners page uses @dnd-kit/core for drag-and-drop reordering. Saves order to DB on drop.
  • Excel export: Each status gets its own sheet with a matching tab colour. The "Dashboard" sheet has merged cells and bold formatting for summary stats.

Responsive breakpoints

Standard Tailwind breakpoints — sm (640px), md (768px), lg (1024px). The storefront shop grid goes from 1 column on mobile to 2 on tablet to 3 on desktop. The admin sidebar hides below md and becomes a hamburger menu.

Security

Security & protection

Contact form - spam protection

Two layers:

  • Honeypot field: A hidden input called website is in the form but invisible to real users (CSS display:none). Bots fill it in. The API route checks — if it has a value, silently return 200 without processing.
  • IP rate limiting: Max 3 submissions per IP per hour. Tracked in a server-side Map (resets on server restart). Stops someone submitting the form in a loop.
apps/storefront/src/app/api/contact/route.ts - spam checks 
// Honeypot check
const honeypot = body.website;
if (honeypot) return NextResponse.json({ ok: true }); // silent success

// Rate limit check
const ip = req.headers.get('x-forwarded-for') ?? 'unknown';
const count = rateLimitMap.get(ip) ?? 0;
if (count >= 3) {
  return NextResponse.json({ error: 'Too many requests' }, { status: 429 });
}
rateLimitMap.set(ip, count + 1);
setTimeout(() => rateLimitMap.delete(ip), 60 * 60 * 1000); // reset after 1 hour

Stripe webhook signature verification

Anyone can POST to /api/payments/stripe/webhook. Stripe signs every webhook payload with the webhook secret. The handler verifies the signature before doing anything — if it doesn't match, it returns 400 and ignores the request.

stripe webhook verification 
const sig = req.headers.get('stripe-signature')!;
const body = await req.text();

let event: Stripe.Event;
try {
  event = stripe.webhooks.constructEvent(body, sig, process.env.STRIPE_WEBHOOK_SECRET!);
} catch {
  return NextResponse.json({ error: 'Invalid signature' }, { status: 400 });
}

Admin authentication - two layers

Getting into the admin panel requires passing two separate checks. Both run on the server before any page content loads.

  1. Clerk session: Must be logged in. The middleware calls auth() — no valid session means redirect to login.
  2. Admin whitelist: The logged-in user's Clerk ID must be in ADMIN_USER_IDS (env var, comma-separated). Being logged in is not enough — only specific accounts can access admin.
apps/admin/src/lib/require-admin.ts 
export async function requireAdmin(): Promise<string | null> {
  const { userId } = await auth();
  if (!userId) return null;

  const allowedIds = (process.env.ADMIN_USER_IDS ?? '')
    .split(',')
    .map(id => id.trim());

  return allowedIds.includes(userId) ? userId : null;
}

// In every admin API route:
const adminId = await requireAdmin();
if (!adminId) return NextResponse.json({ error: 'Forbidden' }, { status: 403 });

Service role key - never in the browser

The Supabase service role key bypasses all row-level security. It lives only in server-side code (API routes and server components). It's never passed to the browser and never stored in a variable prefixed with NEXT_PUBLIC_.

Image upload validation

The upload route checks file size (max 10MB) and MIME type before sending to Supabase Storage. It only accepts image/jpeg, image/png, and image/webp. Anything else gets a 400 before touching storage.

PayHere hash verification

PayHere signs the notify callback with an MD5 hash of the order amount, currency, and merchant secret. The notify route verifies this hash before updating the order status — otherwise anyone could POST a fake "payment successful" to that URL.

Running the project

Docker Compose explained

If you've never used Docker before: Docker lets you run software in isolated boxes called containers. Each container has its own copy of everything it needs to run — the OS libraries, the runtime, the config. You don't install Postgres or Kafka on the server; you run them as containers instead.

Docker Compose is a tool that lets you define multiple containers in one file (docker-compose.yml) and start them all together with one command. It also handles the networking between them — containers can talk to each other by name without knowing each other's IP addresses.

How the Dockerfile works

Each Next.js app has its own Dockerfile. It's a multi-stage build — first it compiles the TypeScript, then it copies only the compiled output into a smaller final image.

apps/storefront/Dockerfile - simplified 
# Stage 1: build
FROM node:20-alpine AS builder
WORKDIR /app
COPY . .
RUN npm install -g pnpm
RUN pnpm install --frozen-lockfile
RUN pnpm run build --filter=storefront

# Stage 2: run (smaller image, no dev tools)
FROM node:20-alpine AS runner
WORKDIR /app
COPY --from=builder /app/apps/storefront/.next/standalone ./
COPY --from=builder /app/apps/storefront/.next/static ./.next/static
COPY --from=builder /app/apps/storefront/public ./public
EXPOSE 3000
CMD ["node", "server.js"]

The .npmrc copy fix

The monorepo uses a .npmrc file at the root that tells pnpm how to install packages. Without it, the Docker build fails because pnpm can't find the workspace packages. The Dockerfile explicitly copies .npmrc before running pnpm install.

Volumes - where data lives

If a container restarts, everything inside it is gone unless it's in a volume. Three named volumes persist data between restarts:

  • postgres-data - mounted into the Postgres container at /var/lib/postgresql/data
  • storage-data - mounted into supabase-storage at /var/lib/storage
  • kafka-data - mounted into the Kafka container at /var/lib/kafka/data

These volumes live on the VPS disk at /var/lib/docker/volumes/. If you ever need to wipe the database and start fresh, you'd delete the postgres-data volume. Be careful.

The internal network

All containers join a Docker network called staticwears-net. On this network, containers can reach each other by name. So the storefront container can call http://kong:8000 and Docker routes it to the Kong container. From outside Docker, none of these internal ports are accessible — only Nginx's ports 80 and 443 are published to the host.

Environment variables in Docker

The docker-compose.yml uses an env file: --env-file .env.supabase. This file lives on the VPS (not in the repo) and contains all the secrets. The compose file passes them into each container using environment: blocks.

docker-compose.yml - how env vars reach the storefront container 
services:
  storefront:
    build:
      context: .
      dockerfile: apps/storefront/Dockerfile
    environment:
      - NEXT_PUBLIC_SUPABASE_URL=${NEXT_PUBLIC_SUPABASE_URL}
      - SUPABASE_SERVICE_ROLE_KEY=${SUPABASE_SERVICE_ROLE_KEY}

      - CLERK_SECRET_KEY=${CLERK_SECRET_KEY}

    networks:
      - staticwears-net
    depends_on:
      - kafka
      - supabase-kong

Common issues

Storefront / Admin shows error page

  • Check logs: docker compose logs storefront
  • Usually a missing env variable - look for undefined in the error
  • Rebuild after env changes: docker compose build storefront && docker compose up -d storefront

Kafka not connecting / email-worker keeps restarting

  • Kafka takes ~30 seconds to be ready after starting. The email-worker retries automatically.
  • If it keeps failing: docker compose restart kafka, wait 30 seconds, then docker compose restart email-worker
  • Check Kafka logs: docker compose logs kafka

Supabase API returning 401 or 403

  • The service role key is wrong or missing. Check SUPABASE_SERVICE_ROLE_KEY in your .env.supabase.
  • Make sure the apps are using createSupabaseAdminClient() in API routes, not the browser client.

Images not loading / 404 on storage URLs

  • The image URL uses the internal Docker URL (kong:8000) instead of the public URL. This happens if the URL rewrite in the upload route is broken.
  • Check that NEXT_PUBLIC_SUPABASE_URL is set to the public URL (https://api.staticwears.com), not the internal one.

SSL certificate expired

renew SSL manually 
docker compose exec nginx certbot renew
docker compose restart nginx

Build fails with "workspace:* not found"

This happens when the Docker build can't resolve local pnpm workspace packages. Make sure the .npmrc file at the repo root is being copied into the Docker build context. It should already be in the Dockerfile — if it's not, add COPY .npmrc . before RUN pnpm install.

GitLab pipeline fails on deploy

  • SSH key issue: Check VPS_SSH_KEY_B64 is set in GitLab CI/CD variables and hasn't expired.
  • VPS unreachable: VPS_HOST and VPS_USER must be correct.
  • Git pull fails: Someone may have force-pushed. SSH into VPS and run git fetch && git reset --hard origin/main from the project directory.

Package

kafka

Kafka is a message queue. Instead of the storefront directly calling the email service (which would slow down checkout), it drops a message into Kafka and moves on. A separate worker process picks up the message and sends the email.

This is called an event-driven architecture. The storefront doesn't care whether the email got sent - it just fires the event and forgets about it.

Topics

Kafka organises messages into topics - basically named channels. This project has three:

packages/kafka/src/topics.ts 
export const TOPICS = {
  ORDER_PLACED:          'order.placed',          // sends order confirmation email
  ORDER_STATUS_CHANGED:  'order.status.changed',  // sends shipping update email
  STOCK_LOW:             'stock.low',             // sends low stock alert to admin
};

Publishing an event

The storefront calls publishEvent() after creating an order. It connects once, sends the message as JSON, and disconnects. The worker container on the other end is always listening.

packages/kafka/src/producer.ts - simplified 
export async function publishEvent(topic: string, payload: object) {
  await producer.connect();
  await producer.send({
    topic,
    messages: [{ value: JSON.stringify(payload) }],
  });
}

The email worker

This runs as its own Docker container - email-worker. It subscribes to all three topics and routes each message to the right email function.

packages/kafka/src/workers/email.ts - simplified 
consumer.subscribe({ topics: Object.values(TOPICS) });

await consumer.run({
  eachMessage: async ({ topic, message }) => {
    const payload = JSON.parse(message.value.toString());

    if (topic === TOPICS.ORDER_PLACED) {
      await sendOrderConfirmation(payload);
    } else if (topic === TOPICS.ORDER_STATUS_CHANGED) {
      await sendShippingUpdate(payload);
    } else if (topic === TOPICS.STOCK_LOW) {
      await sendLowStockAlert(payload);
    }
  },
});

export async function createOrder({ customer_id, items, shipping, notes }) {
  const supabase = createSupabaseAdminClient();

  // 1. Insert the order header
  const { data: order } = await supabase
    .from('orders')
    .insert({ customer_id, ...shipping, notes, status: 'pending', total })

  // 2. Insert all the line items

Middleware (proxy.ts)

Next.js runs proxy.ts on every request before the page renders. This is where protected routes are enforced. If someone tries to go to /checkout without being logged in, they get sent to /login?redirect_url=/checkout first.

apps/storefront/src/proxy.ts 
const isProtected = createRouteMatcher([
  '/account(.*)',
  '/orders(.*)',
  '/checkout(.*)',
]);

export default clerkMiddleware(async (auth, req) => {
  if (!isProtected(req)) return;   // not a protected route - let it through

  try {
    const { userId } = await auth();
    if (!userId) {
      const url = new URL('/login', req.url);
      url.searchParams.set('redirect_url', req.nextUrl.pathname);
      return NextResponse.redirect(url);
    }
  } catch {
    const url = new URL('/login', req.url);
    url.searchParams.set('redirect_url', req.nextUrl.pathname);
    return NextResponse.redirect(url);
  }
});

Auth flow

Clerk handles everything. The app just reads what Clerk provides - it doesn't store passwords or sessions manually.

The sso-callback page reads the redirect_url query param and tells Clerk where to send the user after auth completes. This is how going to /checkout while logged out, then Google OAuth, lands back on /checkout.

Protected routes

The middleware (proxy.ts) intercepts every request. For the three protected paths (/account, /orders, /checkout), it calls auth() from Clerk. If there's no valid session, it redirects to login. If there is one, the page loads normally.

After Clerk verifies the user, the admin middleware checks whether their Clerk user ID is in the ADMIN_USER_IDS env var (a comma-separated list). If it's not there, they get the unauthorized page.

How it works

Order flow

This is the most important flow in the whole app. Here's exactly what happens from the moment someone clicks "Place Order" to the email landing in their inbox.

->

Step by step

1. User clicks "Place Order"

The checkout page collects the shipping form + selected payment method. It calls createOrder() which POSTs to /api/orders with the cart items, shipping details, and notes.

2. API route authenticates

The route calls auth() from Clerk to get the userId. If there's no session, it returns 401. Otherwise it continues with the userId.

3. Order saved to database

The createOrder() function from order-service inserts two things: one row in the orders table (the header), and one row per cart item in order_items. The total is calculated from the item prices.

4. Kafka event published (fire-and-forget)

apps/storefront/src/app/api/orders/route.ts - Kafka publish 
// fire and forget - the response goes back to the user right away
publishEvent(TOPICS.ORDER_PLACED, {
  orderId: order.id,
  to: clerkUser.emailAddresses[0].emailAddress,
  customerName: clerkUser.firstName ?? 'Customer',
  items: orderItems,
  total: order.total,
  shippingAddress: `${shipping.address}, ${shipping.city}`,
}).catch(console.error);   // don't await - don't block the response

5. Stock check

After publishing the order event, the route also checks the stock level of every ordered variant. If any variant's stock is at or below the threshold (default 5 units), a STOCK_LOW Kafka event is published, which triggers a low-stock alert email to the admin.

6. Email worker picks it up

The email-worker container is always running and consuming from Kafka. When it sees an order.placed message, it calls sendOrderConfirmation() from the email-service package, which calls the Resend API and sends the branded HTML email to the customer.

7. Payment

After the order is created in the DB, the payment flow starts separately. The order gets a payment record linked to it. Payment confirmation updates the order status from pending to confirmed.

How it works

Payment flow

Stripe

Stripe uses a hosted checkout page. The server creates a session with the order ID and line items, gives the browser a URL, and the browser redirects to Stripe's page. When the user pays, Stripe sends a webhook to /api/payments/stripe/webhook which updates the order status. Stripe handles all the card UI - the app never touches card numbers.

PayPal

PayPal works entirely in the browser. The PayPal JS SDK renders the familiar PayPal buttons. When the user clicks Pay, a popup opens, they log into PayPal, and the SDK calls back to the app with a transaction ID. No server redirect needed. The transaction ID gets saved to the payment record.

PayHere

PayHere is redirect-based like Stripe but simpler. The app generates a signed form with the order amount, a merchant ID, and a hash of the order details. The user gets redirected to PayHere's payment page. When they pay, PayHere calls /api/payments/payhere/notify on the server with the result.

All three gateways end up in the same place: the order status in Supabase changes from pending to confirmed, which triggers an ORDER_STATUS_CHANGED Kafka event, which sends the customer a shipping update email.

HTTPS / SSL

Let's Encrypt certificates are stored in a volume and mounted into the Nginx container. Certbot renews them automatically. Nginx handles TLS termination - the apps themselves only speak plain HTTP internally.

Starting fresh on the VPS

manual deploy commands 
cd /home/deploy/staticwears
git pull origin main
docker compose --env-file .env.supabase build
docker compose --env-file .env.supabase up -d
docker image prune -f
Infrastructure

Environment variables

Sensitive config lives in .env.supabase on the VPS - never committed to the repo. Here's what each one does.

VariableWhat it's for
NEXT_PUBLIC_SUPABASE_URLPublic URL of the Supabase Kong gateway (https://api.staticwears.com)
SUPABASE_INTERNAL_URLInternal Docker URL for server-side queries (http://kong:8000) - skips the internet
SUPABASE_SERVICE_ROLE_KEYSecret Supabase key that bypasses all row-level security. Never expose this to the browser.
NEXT_PUBLIC_CLERK_PUBLISHABLE_KEYClerk public key - safe to expose in the browser
CLERK_SECRET_KEYClerk secret key - server-side only
RESEND_API_KEYResend API key for sending emails
ADMIN_USER_IDSComma-separated Clerk user IDs allowed to access the admin panel
ADMIN_EMAILEmail address for low-stock alert emails
KAFKA_BROKERSKafka broker address - inside Docker this is kafka:9092
NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEYStripe public key for the client-side SDK
STRIPE_SECRET_KEYStripe secret key for creating sessions server-side
NEXT_PUBLIC_PAYPAL_CLIENT_IDPayPal client ID for the JS SDK
NEXT_PUBLIC_PAYHERE_MERCHANT_IDPayHere merchant account ID
LOW_STOCK_THRESHOLDUnits remaining before a low-stock Kafka event fires (default 5)

Variables prefixed with NEXT_PUBLIC_ are bundled into the browser JavaScript - anyone can see them in the page source. Never put secret keys in NEXT_PUBLIC_ variables.
